# koishi-plugin-group-assistant

[![npm](https://img.shields.io/npm/v/koishi-plugin-group-assistant?style=flat-square)](https://www.npmjs.com/package/koishi-plugin-group-assistant)

面向 Koishi 的群聊治理插件，帮助群管理员集中处理群消息、刷屏、敏感内容、入群申请和违规记录。

当前版本：**1.1.0**

## 适合什么场景

- 课程群、项目群、社团群等需要自动处理广告和违规消息的群聊。
- 需要区分“确定违规”和“需要结合语境判断”的群聊。
- 需要对同一用户进行分级处罚，而不是每次都使用相同处罚的群聊。
- 需要通过 Koishi Console 管理大量关键词，并查看治理记录的群聊。

## 功能

### 内容治理

插件提供红线词库和敏感词库两种内容规则：

- **红线词库**：命中后立即撤回消息，并按照累计违规次数执行处罚。
- **敏感词库**：命中后进入 AI 复核，适合可能出现在正常讨论、引用或科普语境中的词。
- **关键词提示**：处罚通知中的 `{reason}` 可以显示实际命中的关键词，方便用户理解原因。
- **常见变体识别**：可以识别部分大小写、全半角、空白、标点和简单混淆形式。

### 行为治理

- **瞬时刷屏检测**：处理短时间内连续发送大量消息的情况。
- **长期速率检测**：处理持续一段时间高频发送、但没有集中爆发的情况。
- **持续刷屏处理**：消息持续违规时仍会拦截，不会因为重复触发而不断刷屏提醒。
- **处罚逐步升级**：冷却结束后仍在刷屏，会再次累计违规并进入更高处罚级别。
- **不检测相似复读**：不会因为定时通知、公告重复发送或正常复读内容本身触发治理，行为检测只关注发送频率。

### 分级处罚

管理员可以配置多级处罚，每一级都可以单独设置：

- 触发所需的同类违规次数。
- 警告、禁言或踢出。
- 禁言时长。
- 是否发送群内提醒，以及提醒模板。

默认处罚为：

| 级别 | 同类违规次数 | 处罚 |
| ---: | ---: | --- |
| 1 | 1 次 | 警告 |
| 2 | 3 次 | 禁言 10 分钟 |
| 3 | 5 次 | 禁言 60 分钟 |

红线和行为违规默认会先处理当前消息，再累计违规次数。敏感词只有 AI 确认违规后才会进入处罚流程。

### 词库管理

在 Koishi Console 的“群治理词库”页面可以完成：

- 添加、编辑、启用、禁用和删除关键词。
- 在红线词库与敏感词库之间切换。
- 按关键词搜索。
- 通过 UTF-8 TXT 文件批量导入。
- 按群聊分别管理词库。
- 分页浏览大量关键词，避免一次加载过多内容。

TXT 文件要求：

- 一行一个关键词。
- 使用 UTF-8 编码。
- 空行和以 `#` 开头的行会被忽略。
- 单个文件最大 2 MB，最多 100000 行。
- 单个关键词最多 200 个字符。

词库导入只通过 Koishi Console 完成，不支持机器人消息、下载链接或本地路径导入。

### 审计和违规状态

Console 提供三个视图：

- **词库管理**：管理红线词库和敏感词库。
- **审计记录**：查看命中的消息、违规原因、处理动作、AI 结果和累计次数。
- **违规用户**：查看当前累计窗口内的违规用户，并清零指定用户的累计状态。

审计记录和违规状态均支持分页。审计记录会按照配置自动清理，违规累计状态也会在累计窗口结束后失效。

### 入群和成员管理

- 入群申请可以配置同意暗号，申请内容包含暗号时自动同意。
- 黑名单用户的入群申请会被拒绝。
- 新成员入群后自动发送欢迎语。
- 成员退群后自动发送退群通知。
- 白名单用户跳过自动群治理。
- 群主和群管理员自动跳过自动处罚；如果适配器无法提供管理员身份，可以在配置中补充管理员 ID。

## 快速开始

### 安装

在 Koishi 项目中安装插件：

```bash
npm install koishi-plugin-group-assistant
```

然后在 Koishi 配置中启用 `group-assistant`。插件需要 Koishi 的数据库服务，用于保存词库、审计记录、违规状态和名单。

### 初次使用

1. 打开 Koishi Console，进入“群治理词库”。
2. 在左侧添加并选择需要治理的群聊。
3. 选择“红线词库”或“敏感词库”。
4. 直接添加关键词，或上传 UTF-8 TXT 词库。
5. 在插件配置中选择治理强度和处罚阶梯。
6. 需要使用敏感词 AI 复核时，开启 AI 复核并填写 DeepSeek API Key。

建议先使用“均衡”预设观察一段时间，再根据群聊实际消息量调整。

## 配置说明

配置页面按用途分为五组。

### 基础设置

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `welcomeMessage` | 内置欢迎语 | 新成员入群时发送的内容，支持 `{username}`、`{botName}` |
| `leaveMessage` | 内置退群语 | 成员退群时发送的内容，支持 `{userId}` |
| `botName` | 空 | 欢迎语中的机器人名称 |
| `signal` | 空 | 入群申请同意暗号；为空时不自动同意普通申请 |
| `adminUserIds` | 空数组 | 额外的管理员用户 ID |

### 群治理设置

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 总开关 |
| `governancePreset` | `balanced` | 治理强度：宽松、均衡、严格或自定义 |
| `punishmentLevels` | 3 级 | 累计处罚阶梯；留空时只执行即时处理，不执行累计处罚 |
| `offenseWindowHours` | 24 | 自定义模式下，同类违规的累计时间窗口 |
| `auditRetentionDays` | 30 | 审计记录保留天数 |

### 内容检测

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `contentDetectionEnabled` | `true` | 是否启用红线词和敏感词检测 |

### 行为检测

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `behaviorDetectionEnabled` | `true` | 是否启用行为检测 |
| `burstDetectionEnabled` | `true` | 是否启用瞬时刷屏检测 |
| `sustainedRateDetectionEnabled` | `true` | 是否启用长期发送速率检测 |

### AI 复核

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `aiReviewEnabled` | `false` | 是否对敏感词命中进行 AI 复核 |
| `apiKey` | 空 | DeepSeek API Key |
| `model` | `deepseek-v4-flash` | 可选 `deepseek-v4-flash` 或 `deepseek-v4-pro` |

AI 只处理敏感词命中，不处理红线词和刷屏行为。AI 未启用、未填写 API Key 或复核失败时，敏感词不会自动处罚，但会保留相应记录，方便管理员后续检查。

## 治理强度

| 预设 | 瞬时刷屏判定 | 长期速率倾向 | 适合场景 |
| --- | --- | --- | --- |
| 宽松 | 15 秒内 10 条 | 允许更高持续速率 | 活跃群、通知较多的群 |
| 均衡 | 10 秒内 6 条 | 中等持续速率 | 大多数普通群，推荐起点 |
| 严格 | 8 秒内 4 条 | 较低持续速率 | 广告较多、需要强治理的群 |
| 自定义 | 自己设置 | 自己设置 | 已有真实聊天数据，需要精细调参 |

切换预设即可调整主要治理强度。只有选择“自定义”时，下面的行为参数才会生效。

| 自定义参数 | 默认值 | 说明 |
| --- | ---: | --- |
| `burstWindowSeconds` | 10 | 瞬时刷屏的统计时间范围 |
| `burstMessageCount` | 6 | 在统计时间范围内达到多少条消息后触发 |
| `burstCooldownSeconds` | 60 | 同一轮刷屏再次累计处罚前需要等待的时间；期间仍会拦截消息 |
| `burstRecoverySeconds` | 15 | 多久没有再次达到刷屏条件后，结束当前刷屏状态 |
| `sustainedBucketCapacity` | 30 | 长期速率允许的短时消息额度 |
| `sustainedRefillPerMinute` | 18 | 长期速率下每分钟允许恢复的消息额度 |
| `sustainedConfirmSeconds` | 20 | 持续超出长期速率多久后确认违规 |

## 处罚模板

每一级处罚的 `messageTemplate` 留空时，不发送群内提醒，只执行处罚。

支持的变量：

| 变量 | 含义 |
| --- | --- |
| `{at}` | 被处罚用户的 @ |
| `{reason}` | 处罚原因；内容违规会附带命中的关键词，行为违规会显示行为原因 |
| `{action}` | 当前处罚动作 |
| `{muteMinutes}` | 禁言时长 |
| `{offenseCount}` | 当前同类违规次数 |
| `{level}` | 当前处罚级别 |

示例：

```text
{at} 因【{reason}】已被禁言 {muteMinutes} 分钟，当前同类违规 {offenseCount} 次。
```

处罚级别会按照触发次数从低到高生效。违规次数增加后，插件会选择已经达到的最高级别，不会因为配置顺序导致处罚降级。

## 管理员指令

以下指令需要群主、群管理员或 `adminUserIds` 中的管理员执行。

### 审计和违规状态

```text
违规记录
违规记录 -n 20

违规用户
违规用户 -n 20

违规清零 <userId>
```

- `违规记录`：查看最近的治理记录，最多 30 条。
- `违规用户`：查看当前累计窗口内仍有效的违规用户。
- `违规清零 <userId>`：清除指定用户当前的累计违规状态，不删除历史审计。

### 白名单和黑名单

```text
白名单.添加 <userId> [原因]
白名单.删除 <userId>
白名单.列表

黑名单.添加 <userId> [原因]
黑名单.删除 <userId>
黑名单.列表
```

白名单用于跳过自动治理。黑名单用户的消息会被撤回，入群申请会被拒绝，并会参与违规累计。

### 手动处置

```text
警告 <userId> [原因]
处罚 <userId> [原因] -a warn
处罚 <userId> [原因] -a delete
处罚 <userId> [原因] -a mute
处罚 <userId> [原因] -a kick
```

手动处置同样会写入审计并参与累计处罚。手动 `delete` 没有指定目标消息时，只记录审计，不会撤回历史消息。

## 权限和注意事项

- 群主、群管理员默认跳过自动治理，不需要手动加入白名单。
- 如果当前适配器无法识别管理员角色，将管理员 ID 填入 `adminUserIds`。
- 自动撤回、禁言和踢出依赖机器人账号具备对应群权限。
- 词库建议将“无需结合语境即可确定违规”的词放入红线，将可能出现在正常对话中的词放入敏感。
- 先使用均衡预设运行一段时间，再根据审计记录调整，不建议一开始直接使用严格模式。
- 词库和审计数据依赖 Koishi 数据库，请确保数据库服务正常运行。

## 原理与调参建议

### 一条消息如何被处理

```text
收到群消息
  -> 管理员、白名单检查
  -> 内容检测和行为检测
  -> 选择需要优先处理的风险
  -> 撤回当前消息或进入 AI 复核
  -> 累计同类违规
  -> 执行对应处罚级别
  -> 保存审计记录
```

管理员和白名单用户直接放行。红线词、黑名单和刷屏属于可以立即处理的情况；敏感词先交给 AI 判断，确认违规后再进入处罚流程。

### 内容检测如何判断

内容检测只使用 Console 中维护的红线词库和敏感词库：

- 规则与消息使用一致的文本处理方式，降低简单变体造成的漏检。
- 命中红线时，立即撤回并按内容违规累计。
- 命中敏感时，先等待 AI 判断，避免仅凭一个词误伤正常讨论。
- 一条消息同时命中多个风险时，优先处理确定性更高、处置更强的风险。

因此，词库质量比盲目增加关键词更重要。红线词库应保持少而准确，敏感词库可以覆盖需要语境判断的词。

### 短期和长期刷屏的区别

- **短期刷屏**关注“短时间内突然发很多条”，适合处理连续发送广告、刷屏图片或拆分消息。
- **长期速率**关注“持续保持较高发送速度”，适合处理慢速、持续发送的广告或骚扰。
- 两种检测可以同时开启，分别覆盖突然爆发和持续超速两类行为。
- 检测只看发送频率，不看消息内容相似度，因此正常定时通知不会因为文本重复本身触发。

### 冷却、恢复和违规累计

这三个参数作用不同：

- **冷却时间**：同一轮持续刷屏时，消息仍会被拦截，但不会每条消息都新增一次处罚。
- **恢复时间**：用户停止达到刷屏条件一段时间后，结束当前刷屏状态。
- **违规累计窗口**：决定历史违规多久后不再计入累计处罚。

恢复当前刷屏状态不会清除已有违规次数。只有累计窗口结束，或者管理员执行“违规清零”，违规次数才会重新开始计算。

### 如何选择参数

- 普通群：使用均衡预设。
- 消息较多但大部分是正常交流：使用宽松预设，或增大 `burstMessageCount`。
- 广告和拆分消息明显：使用严格预设，或缩短 `burstWindowSeconds`。
- 误伤正常通知：增大 `burstMessageCount`、`sustainedConfirmSeconds`，并将通知账号加入白名单。
- 细水长流的广告：降低长期速率阈值，或缩短长期超速确认时间。
- 处罚过于频繁：增大 `burstCooldownSeconds`；处罚升级太慢则适当缩短冷却时间。
- 处罚次数不符合预期：检查 `offenseWindowHours` 和处罚级别的 `offenseCount`。

建议每次只调整一个或两个参数，并通过审计记录观察一段时间，再继续调整。
